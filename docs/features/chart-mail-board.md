# Chart Mailing 게시판

## 동작

메인 화면의 **Chart Mailing 게시판**(`/chart-mail-board`, 호환 경로 `/fdc_trend/chart-mail-board`)에서 차트 메일 발송 건을 조회한다. 별도 글쓰기·댓글·삭제·SKIP·재발송 버튼은 제공하지 않는다.

- 로그인 사용자 모두 게시글·이미지를 조회하고 **진행중 / 완료**를 변경할 수 있다. 완료 후 진행중으로 되돌릴 수 있다.
- 상태 변경자, 변경 시각과 선택 코멘트(최대 1,000자)를 기록한다. 상세 화면에는 최신 변경 이력 100건을 표시한다.
- 메일 제목, 차트 정보, 발신자, 발송 당시 최종 수신인, 코멘트, 차트 링크와 **메일에 사용한 PNG 원본**을 보관한다. 발송 당시 내용은 수정하지 않는다.
- 이미지는 `MEDIUMBLOB`에 바이너리로 저장한다. 이미지 파일을 별도 디렉터리에 저장하지 않으며 기존 차트 원본이 사라져도 DB에서 조회한다. 최대 5MiB 제한은 기존 발송 제한과 같다.
- 목록은 20건 단위이며 라인·SDWT, 업무 상태, 제목·발신자·차트 정보 검색을 함께 적용할 수 있다. 라인을 선택하면 해당 라인에 등록된 SDWT만 제공하며 라인 변경 시 SDWT와 페이지를 초기화한다. SDWT만 선택해서 전체 라인을 조회할 수도 있다.
- 필터 선택지는 현재 페이지·업무 상태·검색어와 무관하게 등록된 게시글 전체에서 조회한다. 목록·상세에 라인과 SDWT를 표시한다. 목록·상세 JSON에는 이미지 본문을 포함하지 않고 상세 화면에서 인증된 이미지 API를 별도로 조회한다.
- 새 게시글의 `line`·`sdwt`는 발송 당시 차트 링크에서 자동으로 추출한다. 라인은 `line` 파라미터를 사용한다. SDWT는 `chart`의 원본 경로(`erd`·`common`·`erd_commonality`의 날짜 다음 디렉터리)를 우선하며, 경로에서 확인할 수 없으면 `sdwt` 파라미터를 사용한다. 따라서 `MY EQP`·`SKIP LIST`에서 발송한 글도 실제 차트의 SDWT로 분류한다. 해당 화면 분류 값만 있고 실제 SDWT를 확인할 수 없으면 빈값으로 남긴다.
- 작성창에서 별도 입력하지 않는다. 링크에 값이 없거나 200자를 초과하거나 제어문자가 포함된 값은 빈값으로 저장하고 화면에 `미지정`으로 표시한다. 해당 글도 전체 목록에서는 조회할 수 있다. 라인 표시는 다른 화면과 동일하게 `formatLineDisplayName`을 사용한다.
- 같은 차트를 다시 발송하면 새 게시글을 만든다. 같은 사용자·요청 ID의 중복 요청은 새 게시글이나 메일을 만들지 않는다.

## 발송과 저장 순서

1. 기존 SSO·메일 설정·수신인·본문·PNG 검증을 수행한다.
2. 기존 로컬 중복 방지 기록을 생성한다.
3. 게시글, 실제 수신인 목록과 PNG를 **같은 DB 트랜잭션**으로 저장한다. 최초 업무 상태는 `IN_PROGRESS`, 메일 상태는 `pending`이다.
4. 보관한 내용과 동일한 메일 본문을 기존 Knox 발송기로 전송한다. 발신자 구성, HTML과 응답 판정 방식은 유지한다.
5. DB와 기존 로컬 기록에 발송 결과를 각각 반영한다. 한쪽 결과 저장이 실패해도 다른 쪽 저장을 시도한다.

DB 저장 실패 시 외부 메일 API를 호출하지 않는다. 이때 로컬 요청 기록은 중복 발송 방지를 위해 남으며, 원인 조치 후 **작성창을 새로 열어** 새 요청을 만든다. DB commit 응답 유실로 게시글만 남은 경우에도 자동 발송하지 않는다.

DB의 요청 고유 키는 동일 발신자·요청 ID의 중복 등록을 막는다. DB에 이미 있는 요청은 로컬 기록 파일이 다른 프로세스에서도 재발송하지 않는다. 같은 ID의 내용이 달라지면 충돌로 거절한다. 기존 로컬 기록 파일의 보존·단일 프로세스 제약은 그대로 유지한다.

메일 거절·타임아웃·프로세스 중단에도 저장된 게시글과 이미지는 남는다. 자동 재발송·대기열 실행은 하지 않는다. 특히 `pending`은 실제 처리 중뿐 아니라 중단으로 결과 확인이 필요한 상태일 수 있다. DB와 외부 메일을 하나의 트랜잭션으로 확정할 수는 없다.

| DB 메일 상태 | 화면 표시 | 의미 |
|---|---|---|
| `pending` | 처리중 / 결과 확인 필요 | 발송 전 저장됨. 진행 중 또는 중단된 요청일 수 있음 |
| `accepted` | 메일전송 완료 | 기존 발송 응답 판정 유지. HTTP 정상 응답이며 API의 `deliveryVerified: false`는 유지 |
| `rejected` | 발송 거절 | 기존 발송기의 확정 거절 분류 |
| `unknown` | 결과 확인 필요 | 타임아웃·연결 유실·판정 불가 응답 등 |

업무 상태 변경은 메일 상태를 바꾸거나 추가 메일을 보내지 않는다. 동시 변경 시 버전 충돌을 반환하고 화면을 새로 조회한다.

## DB 준비와 활성화

[테이블 생성 SQL](./chart-mail-board.sql)은 기존 `DB_INFO_PATH`의 DB를 사용한다. 접속 정보는 기존 `scripts/mailing_registration.py`의 `load_db_info()`를 재사용하며 Python/PyMySQL 외에 추가 패키지는 필요하지 않다.

| 테이블 | 역할 |
|---|---|
| `chart_mail_post` | 고정 발송 내용, 라인·SDWT, 발신자, 요청 해시, 업무·메일 상태, 안전한 발송 진단 |
| `chart_mail_post_recipient` | 발송 당시 수신인 및 순서 |
| `chart_mail_post_image` | 원본 PNG 바이너리, 바이트 크기, SHA-256 |
| `chart_mail_post_history` | 업무 상태 변경 이력 |

1. 운영 담당자가 DB 종류·버전, InnoDB 지원, 대상 DB와 계정 권한을 확인한다. 제공 SQL은 MySQL 기준이며 다른 제품의 호환성은 별도 확인한다.
2. SQL의 테이블 4개를 생성한다. 애플리케이션은 테이블을 자동 생성하지 않는다. 실행 계정에는 각 테이블의 SELECT/INSERT/UPDATE 권한이 필요하다.
3. 5MiB PNG의 SQL 전송·이스케이프 크기를 수용하도록 DB의 `max_allowed_packet`과 프록시의 기존 메일 요청 크기 제한을 확인한다. DB 설정은 이 구현에서 변경하지 않는다. 예를 들어 16MiB 이상의 packet 여유를 검토한다.
4. 코드와 Python helper를 함께 배포하고, 서버 `.env.mail` 또는 프로세스 환경변수에 `CHART_MAIL_BOARD_ENABLED=true`를 설정한 뒤 서버를 재시작한다.

기본값은 `false`다. 테이블 준비 전 기존 정상 메일 기능을 막지 않기 위한 설정이며, 비활성 시 기존 발송만 수행하고 게시판 API는 `503 / BOARD_NOT_CONFIGURED`를 반환한다. 활성화 후에는 DB 저장이 필수이며 파일 저장이나 메일만 발송하는 동작으로 대체하지 않는다.

기존 발송 기록 파일에는 본문·이미지가 없으므로 과거 메일은 복원·이전하지 않는다. 활성화 이후의 새 발송 요청부터 등록한다. 설정 해제 시 DB 데이터는 삭제하지 않는다.

### 기존 게시판의 라인·SDWT 필터 적용

기존 테이블에는 **새 코드 배포 전에** 운영 담당자가 [컬럼·인덱스 추가 SQL](./chart-mail-board-scope-migration.sql)을 1회 적용해야 한다. 미적용 상태에서 새 코드를 배포하면 게시판 조회와 게시판이 활성화된 메일 발송의 DB 저장이 실패한다. 신규 설치는 갱신된 `chart-mail-board.sql`만 사용하며 추가 SQL을 중복 실행하지 않는다.

1. 대상 DB·백업·ALTER 권한과 복합 인덱스 길이 지원(utf8mb4 최대 약 1,608바이트)을 확인한 뒤 추가 SQL을 실행한다. DDL은 자동 실행하지 않으며 MySQL에서는 전체 롤백되지 않는다.
2. 기존 글을 필터 대상으로 포함하려면 프로젝트 루트에서 아래 보완 스크립트를 실행한다. 기존 `DB_INFO_PATH`와 PyMySQL을 사용한다.
3. 보완 후 새 코드와 Python helper를 함께 배포한다. 이전 코드가 보완 도중 새 글을 등록했다면 배포 후 스크립트를 한 번 더 실행해 누락된 값을 채운다.

```bash
# 안내만 출력하며 DB에 접속하지 않는다.
python3 -B scripts/backfill_chart_mail_board_scope.py

# 운영 담당자가 컬럼 추가를 확인한 뒤 기존 글의 빈값만 보완한다.
python3 -B scripts/backfill_chart_mail_board_scope.py --apply
```

저장된 `chart_url`을 URL 디코딩하여 라인·SDWT를 200건씩 보완한다. 이미 채워진 값과 본문·이미지·수신인·상태·버전·변경 시각은 유지한다. 일부 묶음 처리 후 실패해도 재실행할 수 있다. 링크에서 확인할 수 없는 값은 추측하지 않고 `미지정`으로 남긴다. 코드 구현 과정에서는 운영 DB의 DDL이나 보완 작업을 실행하지 않는다.

### Python으로 테이블 생성

프로젝트 루트에서 `scripts/create_chart_mail_board_tables.py`를 사용할 수 있다. 기존 `DB_INFO_PATH` 설정(기본 `/appdata/l0_spider/db_info.pkl`)과 PyMySQL을 사용하며 위 SQL을 그대로 읽는다.

```bash
# SQL 미리보기만 수행하며 DB에 접속하지 않는다.
python3 -B scripts/create_chart_mail_board_tables.py

# 운영 담당자가 대상 DB와 CREATE 권한을 확인한 뒤 실제 생성한다.
python3 -B scripts/create_chart_mail_board_tables.py --apply
```

다른 접속 설정 파일을 사용하면 다음처럼 지정한다. 예시 경로는 실제 접속 설정 파일 경로로 바꾼다.

```bash
DB_INFO_PATH=/경로/db_info.pkl \
python3 -B scripts/create_chart_mail_board_tables.py --apply
```

대상 테이블이 하나라도 이미 있으면 실행을 중단하며, 기존 테이블을 삭제하거나 변경하지 않는다. MySQL DDL은 전체 롤백되지 않으므로 도중 실패 시 이미 생성된 테이블은 남는다. 성공 출력과 DB 구조를 확인한 뒤 누락 테이블만 SQL로 생성한다. 스크립트는 게시판 활성화 설정이나 서버를 변경하지 않는다.

생성이 완료되면 `게시판 테이블 4개를 생성했습니다.`가 출력된다. 서버의 `.env.mail`에 다음 값을 설정하고 기존 운영 절차에 따라 서버를 재시작한다.

```dotenv
CHART_MAIL_BOARD_ENABLED=true
```

프로세스 환경변수에도 같은 항목이 설정되어 있다면 `.env.mail`보다 우선하므로 값을 함께 확인한다. 생성 시 별도 `DB_INFO_PATH`를 지정했다면 서버에도 같은 경로를 설정한다. 활성화 후 로그인하여 메인 화면의 **Chart Mailing 게시판** 목록이 열리는지 확인한다. 과거 발송 내역은 자동 등록되지 않으며 활성화 이후 새 발송 건부터 저장한다.

이미지와 기록은 자동 만료·삭제하지 않는다. 보존 정책 확정 전에는 DB 백업과 이미지 증가량을 함께 관리한다. 구현 과정에서 운영 DB·실제 메일·`/appdata`에 테스트 작업을 수행하지 않았다. 실제 DB 버전, 테이블 생성, packet 설정과 운영 연결은 미검증이다.

## API와 접근 제어

모든 API는 서버 SSO 로그인을 요구한다. 기존 전역 SSO의 변경 요청 출처 검사를 유지한다. 요청 body의 사용자 ID로 인증하거나 상태 변경자를 지정하지 않는다.

| 요청 | 동작 |
|---|---|
| `GET /api/chart-mail-board?page=1&status=&search=&line=&sdwt=` | 필터를 모두 적용한 목록·총 건수. 상태는 빈값/`IN_PROGRESS`/`COMPLETED`, 검색·라인·SDWT 각각 최대 200자. 라인·SDWT는 빈값이면 전체, 지정하면 정확히 일치하는 글 조회 |
| `GET /api/chart-mail-board/{id}` | 고정 메일 내용, 수신인, 상태, 최신 이력 |
| `GET /api/chart-mail-board/{id}/image` | 인증 후 `image/png` 원본. `private, no-store`, `nosniff`, 제한 CSP 적용 |
| `PATCH /api/chart-mail-board/{id}` | `{status, version, comment?}`로 업무 상태 변경 |

인증 없음 401, 설정 미완료 503, 잘못된 입력 400, 없는 게시글 404, 버전 충돌 409, DB 오류 500을 반환한다. DB 오류 원문·접속 정보·이미지·수신인은 로그나 오류 응답에 넣지 않는다.

목록·상세 게시글에 `line`, `sdwt` 문자열이 추가된다. 목록의 `filters: {lines: string[], sdwts: string[]}`는 비어 있지 않은 선택지이며 `sdwts`만 요청의 라인 조건에 종속된다. 기존 목록 요청에서 새 파라미터를 생략하면 전체 라인·SDWT를 조회한다.

기존 `POST /api/chart-mail`의 입력은 변경하지 않는다. 신규 DB 등록이 수행된 결과에는 선택 필드 `boardPostId`를 추가하며 성공한 작성창에서 게시판 상세로 이동할 수 있다. 기존 로컬 기록으로 처리된 중복 응답에는 이 필드가 없을 수 있다.

## 검증

- `node --test server/chartMailBoard.test.mjs server/chartMail.test.mjs`: 기존 발송 호환성, 이미지 동일성, 중복·다른 프로세스·저장 실패·결과 불명, 인증과 입력·오류 처리. 외부 메일은 가상 응답만 사용한다.
- `python3 -B -m unittest scripts.chart_mail_board_test scripts.backfill_chart_mail_board_scope_test`: 메모리 SQL에서 게시글·수신인·PNG 원자 저장, 실패 rollback, 중복 키, 상태 변경·충돌·이력, 검색·페이지·라인/SDWT 조합, 전체 선택지 및 기존 글 보완·재실행을 검증한다. SQLite 어댑터는 MySQL의 실제 행 잠금·버전·DDL·인덱스 길이·packet 제한을 검증하지 않는다.
- 브라우저 검증은 가상 API와 사용자만 사용한다. 실제 메일 발송과 운영 DB 저장을 대신하는 검증은 아니다.
