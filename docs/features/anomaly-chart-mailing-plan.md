# 이상감지 차트 메일 발송 및 관리 게시판 구현 검토

> 작성일: 2026-09-14
> 상태: 차트 발송 실환경 성공 확인, DB 게시판 연동 구현(2026-09-18; 테이블 준비·활성화 필요)
> 목적: 사용자와 확정한 요구사항, 권장 구현 방향, 미확인 조건을 후속 개발에 전달한다.
> 아래 현재 구현 범위 외의 내용은 후속 계획이다. 사용자가 실제 Chart Mailing 성공을 확인했으며, 이후 변경은 가상 데이터로 검증한다.

## 0. 현재 구현 범위 (2026-09-18)

사용자는 메일 발송을 우선하고, 발송 메일을 목록으로 보는 게시판은 **메일 발송 기능 성공 후** 구현하도록 범위를 조정했다. 수신인 그룹은 등록 화면의 **Chart Mailing 수신인 등록** 탭에서 관리한다. 기존 **Mailing Report 수신인 등록** 탭과 분리하며 로그인한 `knox_id`별로 소유·조회·수정·삭제한다.

- `MailRecipientGroups`와 `/api/mail-recipient-groups`: 로그인 사용자 개인 그룹의 조회·추가·수정·삭제. 그룹 이름은 1~80자, 그룹당 수신인은 1~100명, 사용자당 그룹은 최대 50개다. Knox ID와 `@samsung.com` 주소를 받아 중복을 제거한다. 동일 사용자의 그룹 이름 중복은 허용하지 않는다.
- 소유자는 서버의 SSO 정보로 결정한다. 클라이언트가 전달한 소유자는 사용하지 않으며 다른 사용자의 그룹은 조회·수정·삭제할 수 없다. 기존 서버의 SSO·요청 출처 검사 아래에서 동작한다.
- 그룹은 기존 Mailing 등록과 동일한 `DB_INFO_PATH`의 DB에 저장한다. `server/mailRecipientGroupsDb.mjs`와 `scripts/mail_recipient_groups.py`가 두 테이블의 조회·추가·수정·삭제를 처리한다. 사용자별 쓰기 잠금과 트랜잭션으로 그룹·수신인 목록을 함께 반영하고, DB 실패 시 파일로 대체 저장하지 않는다.
- 사용자가 수신인 그룹 테이블 생성을 확인하여 [DB 연동 명세](./chart-mail-recipient-groups-db.md)와 [MySQL 생성 SQL](./chart-mail-recipient-groups.sql)에 맞춰 연결했다. 사용자 요청에 따라 앞으로 저장하는 그룹만 DB를 사용하며 기존 `.local/mail-recipient-groups.json` 또는 `MAIL_RECIPIENT_GROUPS_PATH`의 파일은 이전·변경하지 않는다. 화면은 DB 그룹만 조회한다. 실제 운영 DB의 제품·버전·테이블 호환성은 미검증이다.
- `ChartMailDialog`: 자설비·동일성·공통부 이상감지 차트 하단에서 작성창을 연다. 그룹 복수 선택과 Knox ID 직접 입력을 함께 사용할 수 있으며 최종 수신인을 표시한다. 코멘트는 코드에 정의한 3개 문구 중 선택하거나 `직접 입력`으로 최대 2,000자까지 작성한다. 제목은 `[SPIDER] <App이름> 이상감지 / <EQPID> / <SENSOR> 확인 부탁드립니다.`를 기본값으로 제공하며 최대 300자까지 수정할 수 있다. 동일성 App은 별도 EQPID 정보가 없어 사용자 요청에 따라 해당 자리를 생략한다. 코멘트 줄바꿈을 유지하고 미리보기와 메일 본문에서 위아래로 약 3줄(각 60px)의 여백을 둔다.
- 자설비 차트는 현재 확대 상태를 변경하지 않고 전체 범위로 별도 렌더링하여 PNG를 만든다. 기존 화면과 같은 점 표시 규칙을 사용한다. 동일성·공통부처럼 기존 PNG를 표시하는 App은 축소·재인코딩 없이 원본 PNG를 메일 본문에 사용한다. 자설비에서 생성하는 PNG는 1200×480에서 600×240으로 추가 축소했다. 메일 HTML에는 PNG 폭을 명시하고 미리보기에서도 원본 폭보다 늘리지 않는다. 작성창에 준비한 이미지를 그대로 발송 요청에 사용하도록 연결했다. 현재 클라이언트 이미지 제한 5MB는 Knox의 확인된 제한이 아니다.
- 메일 본문과 미리보기에 **차트 링크**·**SPIDER 접속** 버튼을 표시한다. 작성창을 연 서비스 origin을 사용하며, 차트 링크는 해당 App의 Line·SDWT와 차트별 조회 조건을 복원하고 대상 파일이 현재 결과에 있으면 먼저 표시한다. 메인 링크는 같은 origin의 `/`로 연결한다. 차트 데이터는 링크 접속 시점의 조회 결과이므로 원본이 더 이상 제공되지 않으면 이전 차트 복원은 보장하지 않는다. 발송 요청의 선택 필드 `chartUrl`은 HTTP(S) App URL만 허용하고 요청 Origin이 있으면 일치 여부를 확인한다. 링크 없는 기존 요청은 계속 처리한다.
- `/api/chart-mail`은 로그인과 메일 설정을 확인한다. `KNOX_MAIL_ENABLED=true`이고 토큰·System-ID·발신자가 유효하면 GET에 `ready: true`를 반환하여 보내기 버튼을 활성화한다. 비활성·잘못된 설정이면 GET은 `ready: false`, POST는 `503 / MAIL_TRANSPORT_NOT_CONFIGURED`를 반환한다. POST는 서버가 검증한 차트 PNG를 HTML의 Base64 data URL로 넣어 Knox API에 전송한다. **사용자가 Chart Mailing의 실제 동작 성공을 확인했다(2026-09-18).**
- Quality-Hub 기준으로 `.env.mail.example`, 서버의 `.env.mail` 로딩과 `server/knoxMailConfig.mjs`의 인증·SSO 발신자 구성을 연결했다. `server/chartMail.mjs`가 제목·차트 정보·코멘트의 HTML 문자를 이스케이프하고, 비어 있지 않은 코멘트(최대 2,000자)·수신인 1~100명·PNG Base64 형식과 5MB 제한·PNG 헤더와 종료 표식을 검증한다. `contentType: HTML`, `docSecuType: PERSONAL`을 사용한다. 수신인 중복은 제거하고 클라이언트가 보낸 발신자는 사용하지 않는다. 5MB는 앱 제한이며 Knox에서 확인된 제한이 아니다.
- 중복 방지는 `server/chartMailStore.mjs`의 단일 Node 프로세스용 파일 저장소를 사용한다. 기본 `.local/chart-mail-requests.json`이며 `CHART_MAIL_REQUESTS_PATH`로 보존 경로를 지정할 수 있다. 발송 전에 사용자·요청 ID 해시, 본문 해시, 시각·상태와 서버가 생성한 문의 코드를 기록한다. 이후 HTTP 상태·연결 오류 분류·응답 형식·소요 시간 등 허용한 진단 필드만 추가하며, 본문·이미지·주소·토큰·API 응답 원문은 저장하지 않는다. 7일 이내 동일 요청을 재발송하지 않으며 같은 ID로 내용이 바뀌면 충돌로 거절한다. 최대 10,000건이고 보관 기간이 지난 기록은 다음 쓰기 시 정리한다. 기록이 손상되거나 사전 저장에 실패하면 발송하지 않는다. 전송 후 상태 저장 실패 또는 중단으로 남은 pending은 재발송하지 않고 결과 확인을 안내한다. 여러 프로세스의 동시 사용은 지원하지 않는다. 재시작·재배포 후에도 중복 방지가 유지되도록 기록 파일을 보존해야 한다.
- HTTP 2xx의 정상적으로 읽힌 빈 응답·JSON 응답은 기존 API 호환성을 위해 `status: accepted`를 유지하지만 `deliveryVerified: false`를 함께 반환한다. 사용자가 실환경 동작 성공을 확인한 뒤 요청한 문구에 따라 화면에는 **메일전송 완료**로 표시한다. 실패 또는 결과 불명 시에는 **메일전송 실패. 관리자에게 문의바랍니다**를 표시한다. API의 `deliveryVerified: false`와 서버 진단·중복 방지 동작은 유지한다. HTTP 2xx여도 JSON의 명시적 실패 표시, 비JSON·16KB 초과·읽기 실패 응답은 결과 불명으로 처리한다. Knox 고유 응답 코드의 성공값은 아직 확인되지 않았으며 임의로 해석하지 않는다. HTTP 4xx(408 제외)는 거절, 408·5xx·리다이렉트·타임아웃·연결 유실은 결과 불명으로 처리한다. 자동 재시도는 하지 않는다. 작성창도 거절·결과 불명·처리 중·요청 충돌 후 같은 요청의 재발송을 막는다.
- Chart Mailing 게시판과 발송 당시 PNG 원본 DB 보관을 구현했다. 로그인 사용자 모두 조회·진행중/완료 변경이 가능하고 상태 변경 이력을 남긴다. 테이블 4개를 준비한 뒤 `CHART_MAIL_BOARD_ENABLED=true`로 활성화한다. 기본값은 `false`이며 활성화 이후 DB 저장 실패 시 발송하지 않는다. 기존 발송 기록 파일을 이전하거나 자동 재발송·대기열을 실행하지 않는다. 상세 계약과 준비 절차는 [게시판 DB 연동 명세](./chart-mail-board.md), 테이블은 [생성 SQL](./chart-mail-board.sql)을 따른다. 운영 DB 테이블 생성·연결은 미검증이다.

이전 작성창 구현 검증: `node --test server/mailRecipientGroups.test.mjs`, 변경 파일 ESLint, `npm run build`. 브라우저 가상 데이터로 세 앱의 작성창, 그룹 생성·수정·삭제, 그룹·직접 입력 수신인의 중복 제거, 전체 범위 PNG와 기존 확대 상태 보존을 확인했다. 발송 접수 표시는 가상 API 응답으로만 확인했다. 테스트는 임시 디렉터리와 가상 사용자만 사용했으며 실제 DB·메일 시스템에 테스트 쓰기나 발송을 수행하지 않았다.

## 1. 목적과 대상

특정 이상감지 건을 차트 단위로 선택하여, 차트 이미지와 짧은 코멘트를 지정된 사내 수신인에게 메일로 전달한다. 같은 발송 건을 Spider의 별도 게시판에 등록하고 진행 상황을 관리한다.

대상 앱은 다음 세 가지다.

- 자설비 이상감지
- 동일성 이상감지
- 공통부 이상감지

세 앱이 공통 메일 작성창, 개인별 수신인 그룹, 메일 발송 기능과 관리 게시판을 사용한다. 차트 이미지 준비 방식만 앱의 현재 구현에 맞게 연결한다.

## 2. 사용자와 확정한 요구사항

| 항목 | 확정 내용 |
|---|---|
| 시작 위치 | 각 차트 하단에 `메일보내기` 버튼을 둔다. |
| 작성창 | 버튼을 누르면 메일 작성 템플릿이 열린다. |
| 이미지 자동 삽입 | 작성창의 **본문 안에 차트 이미지가 이미 삽입된 상태**를 제공한다. 사용자가 파일을 저장하거나 직접 붙여넣을 필요가 없어야 한다. |
| 이미지 범위 | 해당 차트의 **전체 범위**를 보낸다. 화면에서 확대해서 보고 있는 일부 구간으로 제한하지 않는다. |
| 수신인 지정 | 사전에 저장한 수신인 그룹을 선택하거나 `knox_id`를 직접 입력한다. |
| 그룹 관리 위치 | Mailing Report 수신인 등록과 분리된 **Chart Mailing 수신인 등록** 탭에서 관리한다. |
| 그룹 소유 | 수신인 그룹은 **개인별 관리**다. |
| 코멘트 | 정형 문구를 선택하거나 직접 입력한다. 줄바꿈과 위아래 약 3줄의 여백을 유지한다. |
| 메일 제목 | App·EQPID·Sensor를 포함한 기본 제목을 제공하고 사용자가 수정할 수 있다. |
| 발송 실행 | 작성창에서 내용을 확인한 뒤 `보내기` 버튼으로 발송한다. 차트 하단 버튼을 누르는 것만으로 발송하지 않는다. |
| 발신자 | **보내기 버튼을 누른 로그인 사용자**다. |
| 메일 도착 형태 | 수신한 사내 메일의 **본문 안에서 차트 이미지가 보여야 한다**. 파일 첨부나 게시판 링크만 제공하는 것으로 대체하지 않는다. |
| 게시판 연계 | 발송 전에 해당 건과 PNG 원본을 DB에 보관한다. 테이블 준비 후 `CHART_MAIL_BOARD_ENABLED=true`로 활성화한다. |
| 게시판 업무 상태 | `진행중` / `완료`를 사용한다. 게시판의 `SKIP` 기능은 검토·구현 대상에서 제외한다. |
| 같은 차트 재발송 | 사용자가 다시 발송하면 매번 **새 게시글**을 등록한다. |
| DB | 사용자가 보유한 별도 DB를 활용할 수 있다. 종류·접속 방식은 아직 확인하지 않았다. |

게시판의 `SKIP` 제외는 신규 게시판에 대한 결정이다. 기존 이상감지 앱의 `SKIP` 동작을 변경하는 요구는 아니다.

## 3. 작성창과 이미지 준비

### 3.1. 예정 사용자 흐름

1. 사용자가 특정 차트 하단의 `메일보내기`를 누른다.
2. 해당 차트의 전체 범위 이미지를 준비한다.
3. 작성창 본문에 이미지와 해당 이상건의 기본 정보를 자동으로 넣는다.
4. 사용자가 수신인 그룹 또는 직접 입력한 Knox ID를 지정한다.
5. 제목을 필요에 따라 수정하고, 정형 코멘트를 선택하거나 직접 입력한 뒤 본문을 확인한다.
6. `보내기`를 누르면 새 게시글 등록과 메일 발송을 처리한다.
7. 게시판에서 해당 건을 조회하고 업무 상태를 변경한다.

이미지 준비 중에는 작성창에 로딩을 표시할 수 있다. 이미지가 준비되지 않았거나 생성에 실패한 상태에서는 발송하지 않고 원인 안내와 재시도 수단을 제공하는 방향을 권장한다.

작성창의 별도 미리보기나 첨부파일 목록에만 이미지를 표시하는 것으로 요구를 충족했다고 판단하지 않는다. 실제 작성 본문에 이미지가 들어가야 한다.

### 3.2. 앱별 현재 코드와 구현 방향

| 앱 | 확인한 현재 코드 | 권장 구현 방향 |
|---|---|---|
| 자설비 이상감지 | [FdcTrendPage.jsx](../../src/features/fdc-trend/pages/FdcTrendPage.jsx)의 `ErdScatterCard`에서 Recharts로 차트를 그리며 확대 범위를 관리한다. | 화면의 확대 상태를 변경하지 않고, 같은 차트를 전체 범위로 별도 렌더링한 뒤 PNG로 변환하는 기능을 추가한다. |
| 동일성 이상감지 | [CommonalityAnomalyPage.jsx](../../src/features/fdc-trend/pages/CommonalityAnomalyPage.jsx)의 `CommonalityImageCard`에서 기존 이미지 파일을 표시한다. | 해당 이미지 원본을 확보하여 본문에 삽입한다. |
| 공통부 이상감지 | [CommonAnomalyPage.jsx](../../src/features/fdc-trend/pages/CommonAnomalyPage.jsx)의 `CommonAnomalyImageCard`에서 기존 이미지 파일을 표시한다. | 해당 이미지 원본을 확보하여 본문에 삽입한다. |

전체 범위는 선택한 차트가 대상으로 하는 데이터의 전체 범위를 의미한다. 다른 차트나 앱 전체의 데이터를 추가하는 의미가 아니다. 구체적인 시간 범위·축·표시 항목은 실제 구현 시 차트 데이터 기준과 함께 정의한다.

자설비 차트의 이미지 변환을 구현하고 가상 데이터로 축, 변경점 표시, 색상과 전체 범위 PNG를 브라우저에서 확인했다. 실제 데이터의 밀도와 긴 표시 문구에서도 읽기 좋은지는 운영 환경에서 추가 확인이 필요하다.

`CommonalityAnomalyPage`는 공통부 동일성 이상감지에도 사용되는 공통 컴포넌트다. 구현 시 사용자 요청 대상인 세 앱에 적용되도록 범위를 확인하고, 공통부 동일성 앱까지 자동으로 확장하지 않는다.

### 3.3. 이미지 일관성

작성창에 넣은 이미지를 해당 발송 건의 고정 이미지로 보관하여 메일과 게시판이 동일한 차트를 사용하도록 권장한다. 미리보기 이후 데이터가 갱신되더라도 발송 시 다른 차트로 바뀌지 않아야 한다.

게시판에는 원본 데이터 경로만 저장하지 않고 발송 당시 이미지도 보관해야 한다. 추후 원본이 갱신되거나 없어져도 당시 전달한 내용을 확인할 수 있어야 한다. 이미지 원본은 사용자 요청에 따라 DB BLOB에 저장한다. 보존 기간은 미정이며 자동 삭제하지 않는다.

## 4. Knox 메일 연동: 확인된 사실과 남은 조건

### 4.1. Quality-Hub에서 확인한 방식

참고 저장소는 [Quality-Hub](https://github.com/mlbarod/Quality-Hub)이며, 검토 당시 메일 발송 코드와 본문 변환 코드를 확인했다.

| 항목 | 확인한 사실 |
|---|---|
| API | `POST https://openapi.samsung.net/mail/api/v2.0/mails/send?userId={작성자_Knox_ID}` |
| 인증 | `KNOX_MAIL_TOKEN`을 Bearer 인증에, `KNOX_MAIL_SYSTEM_ID`를 `System-ID` 헤더에 사용한다. |
| 발신자 | 작성자의 Knox ID를 URL의 `userId`와 본문의 `sender.emailAddress`에 일치시켜 사용한다. |
| 주소 구성 | Knox ID를 정규화한 뒤 `{knox_id}@samsung.com`으로 구성한다. |
| 본문 | HTML 본문을 생성한다. |
| 이미지 | 본문의 이미지를 `[이미지: 게시글에서 확인]` 문구로 바꾼다. 이미지 데이터와 첨부파일을 보내는 구현은 아니다. |
| 결과 판정 | HTTP 정상 응답을 접수로 기록하며, 실제 응답 본문과 최종 전달 결과는 검증하지 않는다. |
| 저장·발송 | 게시글 저장 후 서버 메모리에서 비동기 발송한다. DB에 저장하는 발송 대기열은 없다. |

근거:

- [qnaMail.mjs](https://github.com/mlbarod/Quality-Hub/blob/main/server/qnaMail.mjs)
- [qnaMailHtml.mjs](https://github.com/mlbarod/Quality-Hub/blob/main/server/qnaMailHtml.mjs)
- [qnaApi.mjs](https://github.com/mlbarod/Quality-Hub/blob/main/server/qnaApi.mjs)
- [품질VOE Knox 메일 알림 문서](https://github.com/mlbarod/Quality-Hub/blob/main/docs/QNA_MAIL_INTEGRATION.md)

참고 구현은 Knox 공식 규격 자체가 아니다. 위 링크는 `main`을 가리키므로 후속 개발 시 변경 여부를 확인한다.

### 4.2. 보유 인증정보의 의미

현재 참고 코드에서 기본 메일 호출에 사용하는 인증정보는 `KNOX_MAIL_TOKEN`과 `KNOX_MAIL_SYSTEM_ID`다. 별도 SMTP 비밀번호를 사용하는 구조는 아니다.

그러나 이 두 값을 보유한 사실만으로 Spider에서 이미지 포함 발송까지 성공한다고 확정할 수는 없다. 다음 조건이 남아 있다.

- Spider 실행 서버에서 해당 API에 접속할 수 있는지
- 보유 토큰·System ID의 사용 범위가 Spider 환경과 로그인 사용자별 발신을 허용하는지
- Knox ID로 구성한 사내 메일 주소가 대상 사용자에게 맞는지
- 이미지 전송에 별도 API·권한·절차가 필요한지
- 성공·실패 응답을 어떻게 판정하고 전달 상태를 어디까지 확인할 수 있는지

2026-09-17 사용자 요청에 따라 API 주소와 기본 인증은 Quality-Hub 기준으로 준비했다. 저장소 루트의 `.env.mail.example`을 `.env.mail`로 복사한 뒤 값을 입력한다. 실제 `.env.mail`은 Git에서 제외한다. 서버는 시작 시 파일을 읽으며 변경 사항은 재시작 후 반영된다. 기존의 비어 있지 않은 프로세스 환경변수가 우선하고, 기존 `notices.env` 로딩 순서도 유지한다.

| 환경변수 | 용도·기본값 |
|---|---|
| `KNOX_MAIL_ENABLED` | 기본 `false`. 유효한 인증 설정과 함께 `true`로 지정하면 실제 발송을 활성화한다. |
| `KNOX_MAIL_TOKEN` | Bearer 접두사를 제외한 토큰. 활성화 설정 검증 시 필수다. |
| `KNOX_MAIL_SYSTEM_ID` | `System-ID` 헤더 값. `SESSION_ID`와 다르며 활성화 설정 검증 시 필수다. |
| `KNOX_MAIL_TIMEOUT_MS` | 기본 `30000`ms(30초), 정수 `100`~`30000`. 연결·Base64 차트 업로드·응답 읽기를 포함한 외부 메일 API 요청 전체 제한 시간이다. |

API 주소는 `https://openapi.samsung.net/mail/api/v2.0/mails/send`로 서버 코드에 고정하고, `userId`와 `sender.emailAddress`는 서버의 SSO 사용자로 구성한다. 요청 준비 함수는 HTTP `POST`, JSON 본문용 헤더, Bearer 인증과 `System-ID`, 리다이렉트 차단 설정을 제공한다. 본문·이미지 생성과 외부 요청을 연결했으며, HTTP 접수·거절·결과 불명을 구분한다. 자동 재시도는 하지 않는다. Quality-Hub의 `KNOX_MAIL_PORTAL_URL`은 게시글 링크용이므로 현재 Spider 차트 발송 준비 설정에는 포함하지 않았다.

발신자 ID는 [currentUser.mjs](../../server/currentUser.mjs)의 서버 측 로그인 사용자 확인 방식을 활용할 수 있다. 클라이언트가 임의로 보낸 발신자 ID를 그대로 신뢰하지 않는다. 토큰과 System ID는 서버에서만 취급하고 브라우저 번들, `VITE_` 변수, 문서와 로그에 실제 값을 노출하지 않는다.

### 4.3. 본문 이미지 발송 가능 확인과 남은 연동 규격

작성창의 HTML 본문에 이미지를 자동 삽입하는 기능과, Knox를 통해 수신한 메일의 본문에 그 이미지가 표시되는 기능은 별도 검증 대상이다.

**2026-09-16 사용자 확인: 메일 본문에 PNG 이미지를 넣어 발송할 수 있다.** 본문 이미지 발송 가능 여부는 사용자 확인 사항으로 기록한다. 2026-09-17 사용자가 기본 요청 구조를 제공했으며, `contentType: HTML`과 `contents` 내 Base64 PNG data URL을 가정하여 우선 구현하도록 승인했다. 이 가정으로 발송기를 연결했다. 실제 전송 형식이 다르면 이미지 삽입 부분을 수정한다. 사내 수신과 이미지 표시는 아직 미검증이다.

확보할 자료는 사내 Knox 메일 API 문서 또는 본문 이미지 발송에 성공한 코드 예제다. 다음 내용을 확인한다.

| 확인 사항 | 확인할 내용 |
|---|---|
| 본문 이미지 발송 | 사용자 확인 완료. 구체적인 구현 방식은 템플릿·발송 예제 또는 API 문서로 확인한다. |
| 요청 형식 | 이미지 직접 포함, 업로드 후 참조, 첨부 후 본문 참조 등 실제 지원 방식과 필드 |
| 참조 관계 | 이미지 식별자와 HTML 본문을 연결하는 방법. CID 등 특정 방식을 지원한다고 미리 가정하지 않는다. |
| 제한 | 이미지 형식·용량, 전체 메일 크기, 수신인 수 등 적용 제한 |
| 권한 | 현재 인증정보로 사용 가능한지, 별도 권한이나 API가 필요한지 |
| 응답 | 접수·거절·부분 실패의 판정 방식, 발송 식별자·상태 조회·중복 방지 지원 여부 |
| 수신 결과 | 실제 사내 메일 환경에서 차트가 본문에 표시되고 읽을 수 있는지 |

Spider의 기존 이미지 URL을 그대로 본문에 넣는 방식은 로그인·접근 제어 때문에 수신 메일에서 표시되지 않을 수 있다. 본문 표시를 위해 기존 이미지 API의 접근 제어를 해제하는 방향으로 구현하지 않는다.

본문 이미지 발송 가능 여부를 다시 미확인으로 취급하지 않는다. 다만 Spider 기능의 구현 완료 여부는 별도로 검증하며, 파일 첨부나 게시판 링크만 전송한 결과로 본문 이미지 요구사항을 완료 처리하지 않는다.

### 4.4. 메일이 도착하지 않을 때 오류 확인

기존 발송 코드는 외부 API의 HTTP 상태·연결 오류를 기록하지 않고 응답 본문을 버렸으므로, 과거 실패 원인을 기록만으로 복원할 수 없다. HTTP 2xx만으로 표시하던 “접수 완료”도 실제 발송을 확인한 결과가 아니었다. 진단 보완 이후의 요청부터 다음 위치에서 확인한다. 변경 코드를 배포하고 서버를 재시작해야 적용되며, 기존 요청 기록을 지우거나 결과 불명 요청을 자동 재발송하지 않는다.

1. **메일 작성창**: 보내기 후 `accepted` 응답이면 “메일전송 완료”, 실패 또는 결과 불명이면 “메일전송 실패. 관리자에게 문의바랍니다”를 표시한다. 발송 전 설정 오류 안내는 유지하며, 전송 결과의 상세 진단과 문의 코드는 API 응답·서버 로그에서 확인한다.
2. **서버 실행 로그**: `npm start`로 실행했다면 해당 터미널의 표준 출력에서 `[chart-mail]`과 문의 코드를 찾는다. 서비스 관리 도구나 컨테이너로 실행했다면 그 프로세스의 표준 출력 로그를 확인한다. 별도 `mail.log` 파일을 자동 생성하는 방식은 아니다.
3. **요청 기록 파일**: 기본 `.local/chart-mail-requests.json` 또는 `CHART_MAIL_REQUESTS_PATH`가 가리키는 파일의 `diagnostics`에 같은 문의 코드와 허용된 진단 정보가 남는다. 기존 버전 기록에는 이 정보가 없을 수 있다. 파일은 읽기 전용으로 확인한다.
4. **브라우저 개발자 도구**: Network의 `/api/chart-mail` 요청에서 Response를 확인한다. 브라우저가 받은 Spider HTTP 상태와 `diagnostics.upstreamStatus`(사내 메일 API HTTP 상태)는 다를 수 있다. 예를 들어 브라우저 HTTP 502와 본문 `upstreamStatus: 401`은 메일 API 인증 거절이다. 서버·프록시가 HTML 오류 페이지를 반환해도 작성창은 같은 실패 문구를 표시하므로 HTTP 상태는 Network에서 확인한다.

진단 정보는 `requestId`, `upstreamStatus`, `networkCode`, `responseKind`, `apiReportedFailure`, `configField`, `durationMs`, `timeoutMs` 중 허용된 값만 사용한다. 제목·이미지·수신인·발신자·토큰·System-ID 값과 API 응답 원문·자유 형식 오류 메시지는 로그에 남기지 않는다.

| 표시 또는 로그 | 확인할 부분 |
|---|---|
| `disabled` | 서버의 `KNOX_MAIL_ENABLED` 설정과 재시작 여부 |
| `configuration_invalid` | `configField`로 표시한 토큰·System-ID·제한 시간 설정, 또는 발신자 Knox ID |
| HTTP 400 | 본문·수신인·Base64 이미지 등 API 요청 규격 |
| HTTP 401 | 발급 토큰·만료 여부 등 인증 설정 |
| HTTP 403 | System-ID·토큰·발신자에 대한 API 사용 권한 |
| HTTP 413 | 이미지·전체 요청 크기, 프록시 또는 사내 API의 크기 제한 |
| HTTP 429 | API 호출 제한 |
| `ENOTFOUND`, `EAI_AGAIN` | Spider 서버의 사내 API DNS 조회 |
| 인증서 관련 `networkCode` | 서버의 TLS 인증서 신뢰·인증서 만료 |
| `TIMEOUT` | 애플리케이션의 전체 요청 제한 시간 `KNOX_MAIL_TIMEOUT_MS` |
| `UND_ERR_CONNECT_TIMEOUT` | HTTP 클라이언트의 별도 연결 제한. API 연결 경로·프록시·방화벽 등을 확인 |
| `UND_ERR_HEADERS_TIMEOUT`, `UND_ERR_BODY_TIMEOUT` | HTTP 클라이언트의 응답 헤더·본문 대기 제한 |
| `ETIMEDOUT` | 하위 네트워크 계층의 시간 초과 |
| `apiReportedFailure: true` | 응답 JSON에서 명시적인 실패 표시 감지. Knox 고유 규격에 따른 최종 판정은 별도 확인 |
| `http_response_unverified` | HTTP 응답을 받았으나 실제 발송·수신은 미확인 |
| `request_storage_failed`, `result_storage_failed` | 로컬 요청 기록의 읽기·쓰기 상태. 후자는 이미 API 요청을 보낸 뒤 기록에 실패했으므로 수신 확인 필요 |
| `duplicate_suppressed` | 같은 요청 ID를 다시 보내지 않고 이전 결과를 반환함 |

TIMEOUT이 발생한 경우 서버의 `.env.mail`에 다음 값을 설정하고 서버를 재시작한다. 이미지 업로드·응답 대기 시간을 확보하기 위해 기본값을 기존 5초에서 30초로 조정했다. **기존 파일이나 프로세스 환경변수에 `5000`이 남아 있으면 코드의 기본값보다 우선한다.** 프로세스 환경변수도 별도로 설정했다면 함께 확인한다.

```dotenv
KNOX_MAIL_TIMEOUT_MS=30000
```

TIMEOUT 화면의 제한 시간과 로그의 `timeoutMs`로 적용 여부를 확인한다. `durationMs`는 요청 검증 등을 포함한 전체 처리 시간이므로 정확히 제한 시간과 일치하지 않을 수 있다. `upstreamStatus`가 없으면 HTTP 응답 헤더를 받기 전에 중단된 것이며, DNS·TCP·TLS 연결, 업로드 또는 API 처리 대기 중 어느 단계인지는 이 정보만으로 구분할 수 없다. `upstreamStatus`가 있으면 응답 헤더를 받은 뒤 본문을 읽는 중에 중단된 것이다. 30초에서도 계속 발생하면 Spider 실행 서버의 사내 API 연결 경로와 API 응답 시간을 확인해야 한다. 제한 시간 변경은 원인 확정이나 발송 성공 확인을 의미하지 않는다.

**전체 30초 전에 `UND_ERR_CONNECT_TIMEOUT`이 발생하는 경우**: `KNOX_MAIL_TIMEOUT_MS`는 `AbortSignal.timeout()`에 적용하는 전체 요청 상한이다. 현재 코드는 Node.js의 기본 `fetch`를 사용하며 별도 dispatcher나 연결 제한을 지정하지 않는다. Undici에는 별도의 연결 제한이 있고 공식 Connector 문서는 기본값을 10초로 안내한다. 따라서 전체 상한인 30초 전에 연결 시도가 종료될 수 있으며, 전체 시간만 늘려도 이 제한이나 접속 문제는 해결되지 않는다. 실제 기본값은 실행 서버의 Node.js·내장 Undici 버전 및 시작 설정에 따라 확인한다. [Undici Connector 공식 문서](https://github.com/nodejs/undici/blob/main/docs/docs/api/Connector.md)

이 오류는 연결 단계가 완료되지 않았다는 근거다. 토큰 오류나 Base64 거절로 먼저 단정하지 않는다. 같은 서버·컨테이너에서 정상 동작하는 Quality-Hub 또는 Python 호출이 있는지 비교하고, 사내 API로 나가는 경로·프록시 적용·DNS/주소 선택·TLS 연결을 확인한다. 다른 PC에서 성공하는 것은 Spider 실행 서버의 접속 가능성을 증명하지 않는다.

연결 확인용으로 Spider 실행 서버에서 아래 명령을 사용할 수 있다. HEAD 요청만 사용하며 메일·토큰·본문은 보내지 않는다. 사내 API에 대한 이 확인 명령은 개발 환경에서 실제 실행하지 않았다.

```bash
curl -q -sS -I -o /dev/null --connect-timeout 10 --max-time 15 -w 'HTTP %{http_code}\n' https://openapi.samsung.net/mail/api/v2.0/mails/send
```

HTTP 401·403·405 등이라도 반환되면 curl이 사용한 경로에서 HTTP 응답을 받은 것이다. 발송 권한·메일 전달 성공을 의미하지 않으며 프록시가 응답했을 수도 있다. curl도 시간 초과라면 서버의 접속 경로부터 확인한다. curl이나 Python만 성공하면 Node.js 실행 환경의 프록시·인증서·주소 선택 차이를 확인한다. 프록시 주소나 인증정보를 로그·채팅에 공유하지 않는다.

Node.js의 환경변수 프록시 지원은 버전·시작 옵션에 따라 달라진다. 지원 버전에서 `--use-env-proxy` 또는 `NODE_USE_ENV_PROXY=1`은 시작 시 `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`를 읽는다. 애플리케이션이 시작된 뒤 `.env.mail`에서 읽는 것과 같지 않다. 실제 배포에서 승인된 프록시 사용 여부와 Node.js 버전을 확인한 뒤 적용하며, 진단만으로 프록시·방화벽 설정이나 TLS 검증을 임의 변경하지 않는다. [Node.js 공식 문서](https://nodejs.org/api/cli.html#--use-env-proxy)

이미 TIMEOUT으로 기록된 요청은 같은 요청 ID로 다시 보내지 않는다. 제한 시간을 바꾸더라도 자동 재시도하거나 기록을 지우지 않으며, 추가 발송 전에는 먼저 수신 여부를 확인한다.

`success: false`, `ok: false`, 실패 상태 문자열 또는 비어 있지 않은 `error` 등은 일반적인 실패 신호로만 사용한다. 고유 업무 코드가 실패를 뜻하는지 모르는데 임의로 성공·실패로 확정하지 않는다. 실제 미수신 원인은 당시 화면 문구·문의 코드·HTTP 상태·안전한 로그 정보와 사내 API의 응답 규격을 함께 확인해야 한다. Base64 이미지 미지원이라고 먼저 단정하지 않는다.

## 5. 개인별 수신인 그룹과 코멘트

별도 **Chart Mailing 수신인 등록** 탭에서 사용자가 자신의 그룹 이름과 구성원 Knox ID 목록을 관리한다. 그룹 소유자인 로그인 `knox_id`를 화면에 읽기 전용으로 표시한다. 기존 정기 메일 등록 데이터의 의미나 저장 계약은 바꾸지 않는다.

권장 설계는 다음과 같다.

- 그룹 소유자는 서버에서 확인한 로그인 사용자로 기록한다.
- 다른 사용자의 개인 그룹을 임의로 수정하거나 발송에 사용하는 것을 서버에서 제한한다.
- 그룹 선택과 직접 입력으로 만들어진 최종 수신인 목록에서 중복을 제거한다.
- 발송 당시의 실제 수신인 목록을 게시글·발송 이력에 저장한다. 나중에 그룹 구성이 바뀌어도 과거 기록은 바뀌지 않도록 한다.
- 직접 등록한 Knox ID 목록을 사용하면 조직도 조회 API 없이 구현할 수 있다. 부서 구성원 자동 조회는 현재 요구 범위에 없다.

현재 그룹 복수 선택과 직접 입력의 동시 사용을 지원한다. 같은 사용자의 그룹 이름 중복은 허용하지 않으며 그룹당 수신인은 최대 100명이다. DB 구성안에서도 이 제한을 유지한다. 정형 코멘트 목록은 코드에서 관리하며, 작성창에서 직접 입력한 코멘트도 사용할 수 있다.

## 6. 게시판과 발송의 연계

### 6.1. 저장 순서

사용자 관점에서는 한 번의 `보내기`로 처리한다. 구현된 DB 계약과 준비 절차는 [게시판 DB 연동 명세](./chart-mail-board.md)를 따른다. 활성화 시 서버의 처리 순서는 다음과 같다.

1. 로그인 사용자, 수신인, 코멘트, 차트 이미지와 원본 이상건 정보를 검증한다.
2. 이미지 보관을 확보한 뒤, 새 게시글과 발송 요청을 같은 DB 트랜잭션으로 저장한다.
3. DB에 저장된 요청으로 Knox 메일을 발송한다.
4. 같은 게시글에 발송 결과와 안전한 진단 정보를 기록한다.

메일과 DB를 하나의 트랜잭션으로 동시에 확정할 수 있다고 가정하지 않는다. 게시글을 먼저 보관하면 메일이 전달된 뒤 게시판 저장이 실패하여 기록이 누락되는 문제를 줄일 수 있다.

DB 저장 실패 시 발송하지 않는다. 메일 발송 실패 시에는 게시글과 요청을 남겨 결과를 확인할 수 있게 한다. 자동 재발송이나 대기열 처리는 하지 않는다.

사용자 요청에 따라 PNG 원본 바이너리까지 DB에 저장한다. 테이블 생성 SQL은 제공하며 운영 DB에서는 실행하지 않았다.

### 6.2. 업무 상태와 메일 상태

두 상태는 별도로 관리한다.

| 구분 | 내용 | 확정 수준 |
|---|---|---|
| 게시판 업무 상태 | `진행중` / `완료` | 사용자 확정 |
| 최초 업무 상태 | `진행중` | 구현 기본값 |
| 메일 상태 | `pending` / `accepted` / `rejected` / `unknown` | 기존 메일 응답 판정과 일치. 상세 표시는 DB 연동 명세 참조 |

HTTP 정상 응답만으로 최종 수신 완료라고 표시하지 않는다. 시간 초과나 응답 유실은 이미 메일이 접수된 상태일 수도 있으므로 확정 실패와 구분해야 한다.

로그인 사용자 모두 조회·상태 변경할 수 있도록 사용자와 확정했다. 완료 후 진행중으로 되돌릴 수 있고 선택 코멘트를 입력한다. 상태 변경자·변경 시각·이전/이후 상태를 기록한다. 업무 상태 변경 시 추가 메일을 보내는 기능은 요청된 범위가 아니다.

### 6.3. 재발송과 중복 방지

- 사용자가 같은 차트를 의도적으로 다시 발송하면 새 게시글과 새 발송 요청을 만든다.
- 버튼 연속 클릭이나 통신 재시도로 동일 요청이 반복된 경우에는 중복 게시글·중복 발송을 방지한다.
- 이를 위해 사용자 발송 동작마다 요청 식별자를 부여하고, 같은 요청의 재시도에서는 식별자를 유지하는 방향을 권장한다.
- 같은 요청의 기술적 재시도는 기록된 결과를 반환하며 외부 메일을 다시 전송하지 않는다. 의도적인 새 발송과 구별한다.
- 서버 재시작 뒤에도 대기 요청을 확인할 수 있도록 발송 요청을 DB에 보관하는 방향을 권장한다.
- 애플리케이션의 중복 요청 방지만으로 외부 메일의 정확히 한 번 전달을 보장할 수는 없다. Knox의 중복 방지·결과 조회 규격을 확인하고, 결과가 불확실한 경우의 재시도 정책을 정한다.

## 7. 별도 DB 활용과 상세 설계 항목

보유한 별도 DB는 게시판과 개인별 그룹, 발송 기록 저장에 활용할 수 있다. 아래는 필요한 정보의 범주이며 테이블명이나 필수 컬럼을 확정한 스키마가 아니다.

| 정보 범주 | 저장 후보 |
|---|---|
| 게시글 | 원본 앱·이상건 식별정보, 제목·코멘트, 차트 이미지 참조, 발신자, 업무 상태, 생성 시각 |
| 수신인 그룹 | 소유자, 그룹 이름, 구성원 Knox ID, 수정 시각 |
| 발송 당시 내용 | 최종 수신인 목록, 확정 본문·이미지, 사용한 코멘트 |
| 발송 요청·시도 | 요청 식별자, 처리 상태, 시도 시각, 확인된 결과, API가 제공하는 발송 식별자 |
| 상태 변경 이력 | 이전·이후 상태, 변경자, 변경 시각 |
| 코멘트 템플릿 | 정형 코멘트 목록. DB 관리 여부와 관리 주체는 미정 |

게시판 이미지의 DB 보관, 전체 로그인 사용자 권한, 재개·이력과 화면 구성은 구현했다. 아래 항목은 초기 검토 목록이며 확정된 내용은 [게시판 DB 연동 명세](./chart-mail-board.md)를 우선한다. 운영 DB 버전·권한·테이블 준비와 보존 기간은 별도 확인한다.

- DB 종류, 접속 방식, 읽기·쓰기 권한과 테이블 준비 절차
- 이미지 저장 방식·보존 기간·크기 제한
- 게시판 명칭·메뉴 위치, 목록·검색·필터·상세 구성
- 게시글 열람·상태 변경 권한, 완료 후 재개 정책
- 앱별 원본 이상건 식별 방식과 표시할 기본 정보
- 정형 코멘트 목록의 향후 관리 방식
- 그룹 선택 방식과 최종 수신인 확인 절차
- 발송 오류·결과 불명·재시도에 대한 화면과 서버 처리 기준

발신자, 개인별 그룹 관리, 차트 전체 범위, 게시판 `SKIP` 제외, 같은 차트의 새 건 등록은 이미 확정된 사항이다. 후속 개발에서 미정 사항으로 되돌리지 않는다.

## 8. 구현 시 검증 기준

아래는 전체 기능의 검증 기준이다. 현재까지 확인한 범위는 0절과 게시판 DB 연동 명세에 기록했다. 운영 DB 연결·테이블 및 실제 환경 검증은 별도로 수행한다.

- 세 앱에서 차트별 작성창이 열리고 본문 안에 이미지가 자동 삽입된다.
- 자설비 차트를 확대해 둔 상태에서도 작성창에는 해당 차트의 전체 범위가 들어간다.
- 이미지가 준비되지 않은 상태에서 발송되지 않으며, 준비 실패를 사용자가 알 수 있다.
- 작성창·발송 요청·게시판에 보관하는 이미지가 동일하다.
- 발신자는 서버에서 확인한 로그인 사용자이며 임의 발신자 지정이 차단된다.
- 개인별 그룹 접근·수정 권한과 직접 입력 수신인의 검증·중복 제거가 동작한다.
- 같은 차트를 의도적으로 다시 보내면 새 게시글이 생기고, 동일 요청의 중복 실행은 억제된다.
- DB 저장 실패, 이미지 보관 실패, 메일 거절, 응답 유실, 서버 재시작 시 기록과 처리 상태가 일관된다.
- 게시판 업무 상태는 `진행중` / `완료`이며 메일 처리 상태와 혼동되지 않는다.
- 사내에서 승인된 검증 절차로 수신 메일 본문의 이미지 표시와 가독성을 확인한다.

개발 환경에서는 기존 테스트와 최소 synthetic data로 직접 영향 범위를 검증한다. 운영 DB·`/appdata` 파일을 테스트용으로 변경하지 않고, 실제 수신자에게 테스트 메일을 보내지 않는다. 사내 수신 검증은 운영 환경 소유자의 승인된 절차로 별도 수행하며, 결과 확보 전에는 미검증으로 남긴다.

## 9. 이번 검토에서 확인한 범위와 후속 순서

이번 대화의 사전 검토에서 Spider의 차트 표시·사용자 확인 코드와 Quality-Hub의 메일 연동 코드를 읽었다. 당시 로컬 Quality-Hub의 `node --test tests/qna-mail.test.mjs`가 통과했다. 해당 검증은 가상 메일 API 응답을 사용하는 기존 구현 테스트이며, Spider의 새 기능이나 실제 Knox 이미지 발송 성공을 의미하지 않는다.

본문에 PNG 이미지를 넣어 발송할 수 있다는 점은 2026-09-16 사용자가 확인했다. 이후 수신인 그룹과 메일 작성창을 구현했으며 현재 범위는 0절에 기록했다. 템플릿·이미지 전송 규격, Spider에서 연동한 메일의 실제 수신, Spider 환경의 발송 권한·접속, 별도 DB 연결은 아직 확인하지 않았다.

후속 순서는 다음과 같다.

1. 서버의 `.env.mail`에 토큰과 System-ID를 입력하고, 실제 발송을 사용할 때 `KNOX_MAIL_ENABLED=true`로 설정한 뒤 서버를 재시작한다. 기록 파일 보존 경로도 확인한다.
2. 사용자가 사내 환경에서 실제 도착과 본문 이미지 표시를 확인한다. 다른 이미지 형식이 필요하면 제공받은 예제에 맞춰 전송 부분을 수정한다.
3. DB 테이블 생성 여부를 전달받아 개인별 수신인 그룹 저장소를 연결한다.
4. 게시판 테이블 4개를 준비하고 `CHART_MAIL_BOARD_ENABLED=true`로 활성화한다. 게시판·DB 발송 기록은 구현했으며 실제 DB 연결은 미검증이다.

이번 발송 구현은 가상 API와 임시 기록 파일을 사용하는 `server/chartMail.test.mjs`, 인증 설정·기존 개인 그룹 관련 테스트로 검증한다. 실제 사내 API·메일·DB에는 테스트 요청을 보내지 않는다.

기존 정기 리포트·메일 등록 구조는 [mailing.md](./mailing.md)를 참고한다. 이 문서는 차트 단위 수동 발송의 별도 기능 계획이며 기존 메일 등록·MY_EQP·이상감지의 동작과 데이터 계약을 변경하지 않는다.
