# 전문 검수 보고 표준

## 작성 언어와 데이터 보호

모든 보고서는 한글로 작성한다. 파일 경로, 함수명, API 상대 path, 명령, 오류 메시지, 라이브러리와 측정 지표는 원문을 유지할 수 있다. 실제 회사 데이터, 내부 URL·host·IP·port·서버 경로, 실제 식별자, credential, token, secret은 보고서와 아티팩트에 넣지 않는다.

## 역할별 저장 경로

- Browser QA: `reports/browser-qa/YYYY-MM-DD_HHMM_browser-qa-report.md`
- Code Audit: `reports/code-audit/YYYY-MM-DD_HHMM_code-audit-report.md`
- Performance: `reports/performance/YYYY-MM-DD_HHMM_performance-report.md`
- 사람이 검토한 통합 문서: `reports/consolidated/`

## 문제 상태

- `확인됨`: 반복 재현 또는 결정적 코드·측정 근거로 실제 문제가 입증됨
- `잠재 위험`: 위험한 코드나 현상은 있으나 도달 조건·외부 계약·반복 재현이 부족함
- `재현 불가`: 정해진 조건과 횟수로 다시 발생시키지 못함
- `추가 확인 필요`: 요구사항, 외부 계약 또는 환경 정보 없이는 판정할 수 없음

## 심각도

- Critical: 잘못된 공정·설비·센서·등급 범위의 데이터를 정상으로 표시, 데이터 불일치를 숨김, 핵심 서비스 전체 사용 불가, 민감정보 노출, 매우 높은 잘못된 품질 판단 위험
- High: 주요 기능 불가, 자주 발생하는 잘못된 결과, 특정 화면·필터 정합성 오류, stale data 표시, 반복 화면 중단, large에서 실사용이 어려운 병목
- Medium: 일부 조건의 기능 오류, 부족한 오류 안내, 우회 가능한 문제, 큰 유지보수 위험, 일정 규모 이상 체감 저하
- Low: 사소한 UI·접근성, 경미한 로그·경고, 즉시 장애가 아닌 코드 정리 문제

심각도와 재현 신뢰도는 별개이다. Critical 후보라도 증거가 약하면 상태와 신뢰도에 이를 그대로 드러낸다.

## 신뢰도

- 높음: 통제된 반복 재현, 직접 코드 경로 또는 반복 측정과 증거가 일치함
- 중간: 일부 재현 또는 강한 간접 근거가 있으나 조건이 완전히 통제되지 않음
- 낮음: 단일 관찰, 미확인 계약, 적은 표본 또는 환경 제약이 큼

## 품질 규칙

- 한 줄짜리 추상적 지적 대신 재현 조건, 코드 위치 또는 측정값을 포함한다.
- “느리다”는 표현만 쓰지 말고 환경, 횟수, 평균·중앙값·범위를 제시한다.
- “오류 가능성”만 쓰지 말고 관련 코드 경로와 발생 조건을 쓴다.
- 재현되지 않은 문제를 확정하지 않는다.
- 하나의 근거로 과도한 결론을 내리거나 같은 문제를 나누어 수를 부풀리지 않는다.
- 요구사항인지 버그인지 불명확하면 `추가 확인 필요`로 둔다.
- 개선 예상효과를 과장하지 않는다.
- 실행하지 않은 테스트, 실패한 명령, 미검수 영역을 숨기지 않는다.
- API 실패, 변환 실패, 부분 데이터와 판단 불가능을 정상으로 바꾸지 않는다.

## 세 보고서 전달 절차

```text
세 에이전트 검수
→ 역할별 한글 보고서 생성
→ 사용자가 보고서와 민감정보 포함 여부 검토
→ main 브랜치 개발용 Codex에 보고서 전달
→ 중복 및 오탐 재검증
→ 현재 main에서 재현 확인
→ 수정 계획 작성
→ Critical·High부터 수정
→ main 전체 테스트
→ 사용자가 승인한 절차로 mock-agent 최신화
→ 세 에이전트 재검수
```

`mock-agent`나 검수 브랜치를 `main`으로 merge 또는 rebase하지 않는다. 보고서 전달은 코드 병합 권한을 의미하지 않는다. `main` 수정과 Git 작업은 사용자가 개발용 Codex에 별도로 명시적으로 요청해야 한다.

## 메인 개발용 Codex 표준 요청 예시

```text
첨부한 Browser QA, Code Audit, Performance 보고서를 통합 검토해 주세요.

이번 단계에서는 아직 코드를 수정하거나 commit, push, merge하지 마세요.
현재 main의 코드와 테스트를 기준으로 다음만 수행해 주세요.

1. 세 보고서의 중복 항목을 하나의 문제 단위로 묶기
2. 각 항목의 근거와 역할 경계를 비교해 오탐 여부 확인
3. 현재 main에서 재현 가능한지 읽기·테스트 범위에서 확인
4. 확인됨 / 잠재 위험 / 재현 불가 / 추가 확인 필요로 재분류
5. 데이터 정합성 위험을 우선하여 Critical / High / Medium / Low 재산정
6. Critical·High 항목의 수정 계획과 수정 후 검증 기준 작성
7. 보고서 사이의 모순, 필요한 추가 정보, 실행하지 못한 검증 명시

실제 회사 데이터나 내부 주소·식별자를 출력하지 말고, 확인된 사실과 추정을 분리해 한글로 보고해 주세요.
```

## 재검수 완료 조건

수정 후에는 원래 재현 절차, 정상 시나리오, 관련 예외 시나리오와 회귀 테스트를 다시 실행한다. 성능 항목은 동일 환경·동일 데이터 규모·동일 횟수로 전후를 비교한다. 단순히 오류가 사라졌다는 이유만으로 데이터 정합성이나 성능 개선을 완료로 처리하지 않는다.
